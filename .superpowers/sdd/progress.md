## Final whole-branch review (2026-08-10)
After all 17 tasks completed, dispatched a final whole-branch review (opus model) covering Tasks 3-17 as a single unit, per subagent-driven-development's post-plan gate. Found 2 Critical, cross-cutting findings that no single task's scoped review could have caught (each task's action file correctly implemented its own local checks; the gap was structural, spanning auth.ts + guards.ts + all three action files):

1. CRITICAL - Cross-tenant session bypass: src/auth.ts minted tenantSlug/tenantSchema into the session/JWT at login, but nothing ever read it back to validate against the current request's resolved tenant. Every server action derived its tenant purely from the current Host header. Since all tenants share one AUTH_SECRET, a session token from tenant A would decrypt validly and pass requireSession()/requireRole() on tenant B's subdomain, then operate on tenant B's data. Controller independently verified via grep (tenantSchema never read outside auth.ts) before proceeding.
2. CRITICAL - trustHost unset: NextAuth v5 defaults trustHost=false outside dev/Vercel/CF-Pages; production auth on self-hosted infra would throw UntrustedHost on every request. Invisible in local dev.

FIXED in commit 1f0e3d1 (pushed to origin/main): requireSession() in src/lib/auth/guards.ts now also calls resolveTenant() and redirects to /login?error=tenant-mismatch if the resolved tenant's schemaName doesn't match session.user.tenantSchema -- this single choke point covers every action file since all of them route through requireSession()/requireRole() before touching the tenant DB (verified: zero unguarded getTenantDb() call sites). Added trustHost: true to the NextAuth() config in src/auth.ts (NOT AUTH_URL, which would break per-tenant host handling). New tests in guards.test.ts prove the mismatch redirect (RED confirmed against pre-fix code, GREEN after). Independently re-reviewed (opus, adversarial, re-traced the full attack path and all DB-access call sites, ran tsc/tests independently) -- verdict: Resolved, Ready to merge: Yes.

Non-blocking residual items flagged by the fix's re-review for a future hardening pass (Phase 2 or before real production deploy):
- R1: tenantDbOrThrow() in each action file independently re-derives the schema from resolveTenant() again rather than trusting the now-validated session -- two sources of truth that happen to agree today but aren't structurally forced to. Recommended: collapse to a single getTenantDb(session.user.tenantSchema) sourced from the guard's return value, deleting the duplicated tenantDbOrThrow() helper from all three action files.
- R2: redirect()'s NEXT_REDIRECT error is swallowed by try/catch in cliente-actions.ts's createCliente/updateCliente (calls requireRole inside the try) -- a tenant-mismatched or forbidden user sees literal "NEXT_REDIRECT" text instead of being redirected. Fails closed (no DB write happens), so UX bug not security bug. vehiculo-actions.ts/historial-actions.ts don't have this bug (guard called outside try).
- R3: /login?error=tenant-mismatch and ?error=forbidden are never displayed by the login page/form -- locked-out user sees a bare form with no explanation.
- R4: BASE_DOMAIN silently defaults to "zdevs.uk" in middleware.ts if unset -- combined with the new strict guard, a missing/misconfigured BASE_DOMAIN in prod would be a total authenticated-user lockout. Consider failing fast at boot if unset in production.
- R5: local .env (gitignored) contains AUTH_URL="http://localhost:3000", pre-existing and harmless in dev, but a footgun if ever copied into a prod env file (would break per-tenant host handling) -- worth removing or noting not to carry it forward.

Other Important/Minor findings from the whole-branch review (not fixed, deferred as Phase 2 backlog, none blocking):
