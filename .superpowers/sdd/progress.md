## Final whole-branch review (2026-08-10)
After all 17 tasks completed, dispatched a final whole-branch review (opus model) covering Tasks 3-17 as a single unit, per subagent-driven-development's post-plan gate. Found 2 Critical, cross-cutting findings that no single task's scoped review could have caught (each task's action file correctly implemented its own local checks; the gap was structural, spanning auth.ts + guards.ts + all three action files):

1. CRITICAL - Cross-tenant session bypass: src/auth.ts minted tenantSlug/tenantSchema into the session/JWT at login, but nothing ever read it back to validate against the current request's resolved tenant. Every server action derived its tenant purely from the current Host header. Since all tenants share one AUTH_SECRET, a session token from tenant A would decrypt validly and pass requireSession()/requireRole() on tenant B's subdomain, then operate on tenant B's data. Controller independently verified via grep (tenantSchema never read outside auth.ts) before proceeding.
2. CRITICAL - trustHost unset: NextAuth v5 defaults trustHost=false outside dev/Vercel/CF-Pages; production auth on self-hosted infra would throw UntrustedHost on every request. Invisible in local dev.

FIXED in commit 1f0e3d1 (pushed to origin/main): requireSession() in src/lib/auth/guards.ts now also calls resolveTenant() and redirects to /login?error=tenant-mismatch if the resolved tenant's schemaName doesn't match session.user.tenantSchema -- this single choke point covers every action file since all of them route through requireSession()/requireRole() before touching the tenant DB (verified: zero unguarded getTenantDb() call sites). Added trustHost: true to the NextAuth() config in src/auth.ts (NOT AUTH_URL, which would break per-tenant host handling). New tests in guards.test.ts prove the mismatch redirect (RED confirmed against pre-fix code, GREEN after). Independently re-reviewed (opus, adversarial, re-traced the full attack path and all DB-access call sites, ran tsc/tests independently) -- verdict: Resolved, Ready to merge: Yes.

Non-blocking residual items flagged by the fix's re-review for a future hardening pass (Phase 2 or before real production deploy):
- R1: tenantDbOrThrow() in each action file independently re-derives the schema from resolveTenant() again rather than trusting the now-validated session -- two sources of truth that happen to agree today but aren't structurally forced to. Recommended: collapse to a single getTenantDb(session.user.tenantSchema) sourced from the guard's return value, deleting the duplicated tenantDbOrThrow() helper from all three action files.
- R2: redirect()'s NEXT_REDIRECT error is swallowed by try/catch in cliente-actions.ts's createCliente/updateCliente (calls requireRole inside the try) -- a tenant-mismatched or forbidden user sees literal "NEXT_REDIRECT" text instead of being redirected. Fails closed (no DB write happens), so UX bug not security bug. vehiculo-actions.ts/historial-actions.ts don't have this bug (guard called outside try).
- R3: /login?error=tenant-mismatch and ?error=forbidden are never displayed by the login page/form -- locked-out user sees a bare form with no explanation.
- R4: BASE_DOMAIN silently defaults to "zdevs.uk" in middleware.ts if unset -- combined with the new strict guard, a missing/misconfigured BASE_DOMAIN in prod would be a total authenticated-user lockout. Consider failing fast at boot if unset in production.
- R5: local .env (gitignored) contains AUTH_URL="http://localhost:3000", pre-existing and harmless in dev, but a footgun if ever copied into a prod env file (would break per-tenant host handling) -- worth removing or noting not to carry it forward.

## Fase 8 (Notificaciones automáticas al cliente, módulo 6 §5) -- alcance acotado a email/SMTP (decidido 2026-08-21)

**Fase 8 = SOLO notificaciones por email vía SMTP del propio cliente (el taller), no WhatsApp/SMS, no proveedor externo de email.**

- Motivo: evitar costos de servicios externos (SendGrid, AWS SES, Resend, etc.) y de mensajería (Meta/Twilio/360dialog) antes de que el negocio los necesite.
- Cada tenant configura su propio servidor SMTP (host, puerto, usuario, password, fromEmail, fromName) usando el correo corporativo que ya tiene -- no un proveedor centralizado gestionado por el SaaS.
- Librería: Nodemailer (estándar de Node.js, sin costo). Password SMTP encriptado con `crypto` usando una clave maestra en `.env` (nunca en texto plano en la base de datos).
- Plantillas: texto plano o HTML básico en v1 -- no un motor de plantillas complejo.
- **WhatsApp/SMS quedan diferidos a una fase posterior** (candidata: Fase 10), condicionado a: cuenta de Meta Business verificada, presupuesto definido para costo por mensaje, templates aprobados por Meta, y una decisión de intermediario (Twilio, 360dialog) vs. API directa de WhatsApp Business.
- **Explícitamente fuera de Fase 8**: WhatsApp/SMS, SendGrid/AWS SES/Resend (o cualquier proveedor externo de email), motores de plantillas HTML complejos.

Cuando se planifique Fase 8 (después de Fase 7, agendamiento de citas), usar esta sección como el alcance vinculante en lugar de re-derivarlo del design doc, que aún no refleja esta decisión de reducción de alcance.

**ACTUALIZACIÓN (2026-08-21, al planificar Fase 7):** el usuario decidió adelantar el envío real de recordatorios por email a Fase 7, en lugar de dejarlo pendiente para esta Fase 8. Fase 7 construye ahora la infraestructura SMTP/Nodemailer descrita arriba (config SMTP por tenant, password encriptado con `crypto` + clave maestra en `.env`, plantillas de texto plano/HTML básico) para enviar los recordatorios de mantenimiento preventivo. El resto de esta sección (alcance de Fase 8, exclusiones de WhatsApp/SMS) sigue vigente sin cambios: Fase 8 pasa a ser "notificaciones automáticas al cliente sobre el estado de la orden" (módulo 6 §5) **reutilizando** la infraestructura SMTP ya construida en Fase 7, en vez de construirla desde cero.

**CONFIRMADO (al cerrar Fase 7):** la infraestructura SMTP descrita arriba ya existe y está en producción -- ver la sección "TorqueFlow Fase 7" de este mismo ledger para las decisiones vinculantes (singleton ConfiguracionSmtp, sobre AES-256-GCM, cooldown de 90 días, endpoint de cron con CRON_SECRET). ## Cursor-pointer fix, app-wide (2026-09-02, same session)
User reported buttons (e.g. "Nuevo cliente", "Nueva orden") show the default arrow cursor on hover instead of a pointer/hand. Root cause: `src/components/ui/button.tsx`'s shared `buttonVariants` base classes had no `cursor` utility at all -- Tailwind's Preflight resets `<button>` to `cursor: default` (a deliberate, often-overridden choice since Tailwind v3), and since `Button` is the one component every "botón" in the app goes through (including `buttonVariants({})` applied to `<Link>`s styled as buttons), the gap was universal. Fixed directly (commit 5b546ab, pushed, controller-authored, trivial single-file-plus-one CSS fix): added `cursor-pointer` to `buttonVariants`' base classes and `disabled:cursor-not-allowed` alongside the pre-existing `disabled:opacity-50` (matching the same disabled-cursor convention already used in `select.tsx`/`combobox.tsx`). Also fixed the one other real, styled, interactive raw `<button>` in the app missing the same thing: the show/hide-password toggle in `src/app/login/login-form.tsx`. Deliberately left `src/app/(dashboard)/session-renewal-modal.tsx`'s two raw buttons untouched -- that component has zero Tailwind styling at all (not yet wired into the design system), a different and larger problem than a missing cursor utility, out of scope for this fix. tsc clean, full suite 738/756 (only the pre-existing DB-provisioning flake, membership varies as always), browser-verified live via `getComputedStyle(...).cursor` directly (not just visually) on "Nuevo cliente", "Nueva orden", and a disabled pagination button (correctly shows `not-allowed`).
